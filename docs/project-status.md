# 포워딩 시스템 요구사항 및 개발 현황

기준일: 2026-09-28

## 1. 프로젝트 목적과 사용자 요구사항

이력서에 첨부할 포트폴리오용 포워딩 시스템이다. 물류 대기업의 업무 복잡성을
모델링하되, 실제 대기업 규모의 상시 운영 인프라를 구축하는 것이 목적은 아니다.
글로비스와 같은 기업의 업무를 예시로 삼았으며 해당 기업의 내부 시스템을 재현하거나
실제 내부 구조를 확인한 것은 아니다.

### 업무 범위
- 여러 법인이 사용하는 시스템으로 법인별 업무와 데이터를 관리한다.
- 같은 그룹사의 화물뿐 아니라 외부 기업의 화물도 취급한다.
- 자동차 등 완성차와 소형 화물 등 일반 화물을 지원한다.
- 컨테이너 운송은 FCL과 LCL을 모두 지원한다.
- 여러 법인이 하나의 운송에 참여할 수 있는 구조를 지향한다.

### 개발·운영 요구
- 백엔드의 데이터 구조와 업무 경계를 초기부터 설계한다.
- GitHub로 형상관리하고 검증·배포 과정을 자동화한다.
- 로컬에서 개발하고 테스트하는 방식을 기본으로 한다.
- 필요할 때만 개발·시연 환경에 배포하고 기동한다.
- 상시 클라우드 비용을 최소화한다.
- 현재까지의 사용자 요청과 개발 상태를 Markdown으로 기록하고 커밋·푸시한다.
- 앞으로 커밋 제목은 기능명으로 작성하며 이 규칙을 지속 유지한다.

## 2. 합의한 설계 방향 — 아직 구현되지 않은 부분 포함

### 업무 모델
- 고객 운송 주문, 화물, 운송 구간, 실행 단위, 서류, 정산을 분리한다.
- 자동차·일반 화물은 화물 종류이고 FCL·LCL은 적재 방식으로 별도 관리한다.
- 주문 하나를 여러 컨테이너·항차로 나누는 분할을 지원할 수 있어야 한다.
- LCL은 여러 고객 주문을 하나의 컨테이너에 연결하는 혼재를 지원한다.
- 계약 법인, 주문 책임 법인, 구간 수행 법인, 청구·지급 법인을 구분한다.
- 우리 법인 조직과 고객 그룹·고객 법인 조직은 별도로 관리한다.
- 운송 참여 권한과 원가·마진 등 재무 정보 접근 권한을 분리한다.

### 후속 화면·모듈 구성안
업무 홈, 통합 운송 현황, 고객·계약, 운송 주문, 운송 실행, 서류,
정산·손익, 실적 분석, 기준정보·권한, 외부 연동을 후보로 정리했다.
이 목록은 목표 구조이며 구현 완료 목록이 아니다.
Ro-Ro, 차량 VIN·손상 기록, 법인 간 정산, 외부 ERP·선사 연동은 후속 설계 범위다.

### 기술·운영 방향
- Spring Boot 모듈형 모놀리스와 React·TypeScript 프런트엔드.
- PostgreSQL, Flyway 마이그레이션, 로컬 Docker Compose.
- 기능 개발 전에 로그인·법인별 권한 경계를 우선 구현.
- 클라우드는 필요 시 수동 트리거로 생성·배포·삭제하는 데모 환경을 지향.
- AWS 상시 운영안은 초기 참고안이며 현재 구현 범위에서 제외.
- 클라우드 공급자, 서버 사양, 배포 방식은 아직 확정하지 않음.
- Redis, 메시지 브로커, 별도 Worker, Kubernetes는 현재 도입하지 않음.
- 파일 저장 추상화, 기업 SSO, RLS 등은 설계 검토 대상이며 아직 미구현.

## 3. 현재 구현 완료

| 구분 | 구현 내용 |
|---|---|
| 저장소 | `leonjk3/forwarding`, 기본 브랜치 `main` |
| 로컬 경로 | `D:\codex\forwarding` |
| 백엔드 | Java 17, Spring Boot 4.1.1, Maven Wrapper |
| 의존성 | Web MVC, Actuator, JDBC, PostgreSQL, Flyway |
| DB 설정 | 환경 변수 기반 DB 접속, 로컬 주소 기본 바인딩 |
| 마이그레이션 | `V1__create_legal_entities.sql`의 `legal_entity` 테이블 |
| 법인 테이블 | UUID, 고유 코드, 이름, 국가 코드, 생성 시각 |
| 상태 API | `/actuator/health`, 상세 상태 정보 비공개 |
| 프런트엔드 | React·TypeScript·Vite, 한국어 초기 화면 |
| 연결 확인 | 버튼으로 상태 API 호출, 제한 시간과 오류 안내 처리 |
| 개발 프록시 | Vite에서 `/actuator`를 로컬 백엔드로 전달 |
| 로컬 DB | PostgreSQL 17 Compose, 상태 검사, 영속 볼륨 |
| 환경 관리 | `.env.example`, 비밀정보·빌드 산출물 Git 제외 |
| 문서 | README 실행 절차, 아키텍처 결정 문서 |
| CI | main push, PR, 수동 실행 시 백엔드·프런트 검증 |

현재 법인 테이블만 생성하며 데모 법인·사용자 데이터는 없다.
프런트엔드는 초기 연결 확인 화면이며 실제 운송 관리 화면은 아니다.

## 4. 검증 결과와 제약

- 로컬 Maven `verify` 성공. 로컬에서는 DB 통합 테스트가 조건에 따라 건너뛰어졌다.
- 로컬 프런트엔드 `lint`, `build` 성공.
- 최초 GitHub CI에서 백엔드·프런트엔드 작업 모두 성공.
- CI는 PostgreSQL 서비스를 실행하고 `DB_INTEGRATION_TEST=true`로 통합 테스트를 활성화했다.
- 통합 테스트는 법인 테이블 조회와 상태 API HTTP 200 / UP 응답을 검증한다.
- 최초 CI: https://github.com/leonjk3/forwarding/actions/runs/36376469216
- 최초 구현 커밋: `c9eafd2`.
- 로컬 점검 시 Docker 명령을 사용할 수 없어 Compose 실행 검증은 남아 있다.
- 프런트 개발 서버를 실행하고 HTML과 React 모듈의 HTTP 200 응답을 확인했다.
- `frontend/index.html`을 직접 열면 React 앱이 실행되지 않는다. Vite 서버 주소로 접속해야 한다.
- 개발 서버는 프로세스 실행 중에만 접속 가능하며 재부팅 이후 상시 실행을 보장하지 않는다.
- 클라우드 자원은 생성하지 않았고 클라우드 배포 자동화도 아직 구현하지 않았다.
- 최초 CI에 일부 Actions의 Node 런타임 폐기 예정 경고가 있었다. 작업은 통과했으며 후속 정비 대상이다.

## 5. 미구현 사항과 다음 순서

1. Docker 사용 환경 확인 후 로컬 PostgreSQL과 백엔드 통합 실행.
2. 데모 법인·사용자 데이터 및 로그인.
3. 법인 소속·역할·운송 참여 기반 접근 제어와 법인 간 접근 차단 테스트.
4. 운송 주문 등록·목록·상세 조회.
5. FCL·LCL 혼재·완성차별 실행 모델과 화면.
6. 서류 관리, 비용·법인 간 정산.
7. 필요할 때만 생성·배포·삭제하는 클라우드 데모 자동화.

순서는 현재 작업 계획이며 모든 기능의 세부 요구와 일정을 확정한 것은 아니다.

## 6. 커밋 규칙

앞으로 커밋 제목은 변경한 기능이나 결과를 나타내는 한국어 명사구로 작성한다.
유형 접두사 없이 `법인별 접근 권한 관리`, `운송 주문 등록`처럼 작성한다.
문서 변경도 동일하게 적용한다. 기존 최초 커밋은 이 규칙 도입 이전 기록으로 유지한다.
지속 적용할 작업 지침은 저장소 루트의 [AGENTS.md](../AGENTS.md)에 기록한다.
